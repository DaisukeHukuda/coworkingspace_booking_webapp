# TORCH会員予約システム 設計書

- 日付: 2026-07-23
- 対象: TORCH Coworking の月額会員・回数券ユーザー向け利用予約Webアプリ
- 方針決定者: 福田さん（ヒアリング済み）／設計: Claude（Fable 5）

## 1. 目的と成功基準

**目的**: 月額会員・回数券ユーザーの利用予約を、LINE公式アカウントでの手動やり取りから、Webアプリでのセルフサービス（空き確認→リクエスト→確定/否認）に置き換える。

**成功基準**:
1. 会員がLINEで問い合わせることなく、空き確認からリクエスト送信まで自分で完結できる
2. スタッフの対応が「通知メールを受けて、管理画面で確定/否認ボタンを押すだけ」になる
3. （Square同期導入後）Squareで埋まった枠・閉じた枠がアプリの空き表示にも反映され、食い違いが起きない

## 2. 背景と前提（ヒアリングでの決定事項）

| 項目 | 決定内容 |
|---|---|
| 通常客の予約 | Square予約（Appointments）のオンライン予約ページで日付＋時間枠を選ぶ方式 |
| 会員のリクエスト単位 | 日付＋時間枠（Squareと同じ粒度） |
| 会員の本人確認 | 会員ごとの専用リンク方式（ログイン不要。booking-systemの代理店ページで実績あり） |
| 回数券の残数管理 | 初期スコープに含めない。ステップ④で追加 |
| 通知 | メールで自動通知（Resend。booking-systemで実績あり） |
| Square連携の深さ | 読み取りのみ。確定した会員予約をSquareカレンダーへ書き込む必要はない（席数に余裕がある運用のため） |
| 採用案 | 案A: 自作Webアプリ＋Square自動同期。ステップ分割で開発 |

**流用する既存資産**: `Projects/booking-system`（Sup!Sup!用予約管理システム）の技術構成・設計パターン・テスト構成。特に「トークン付き専用リンク」「リクエスト予約の承認/否認」「Resendメール通知（未設定時はスキップ＋ログ）」はほぼ同型。

**SquareのAPI前提**: Bookings APIは日本のSquareアカウントで利用可能（2022年5月GA。出典: developer.squareup.com ブログ「Build With Bookings API, Now Generally Available」）。読み取りに必要なのはアクセストークンのみで費用は無料。

## 3. スコープ外（やらないこと）

- 決済・課金（会費・回数券の販売・オンライン決済）
- 一般客向けの予約機能（従来どおりSquareの予約ページを使う）
- Squareカレンダーへの予約書き込み（読み取り専用）
- LINEへの自動通知（将来の検討課題。当面、結果通知はメール）
- ネイティブアプリ化・プッシュ通知

## 4. 全体像

```
会員（スマホ）                       スタッフ
   │ 専用リンク /m/{token} を開く        │
   ▼                                    │
[会員ページ]                            │
   │ カレンダーで空き確認                │
   │ 日付＋時間枠を選びリクエスト送信 ──→ 通知メール（Resend）
   │                                    ▼
   │                              [管理画面 /admin]
   │                                 承認待ち一覧から
   │ ←── 確定/否認の通知メール ──── 確定 or 否認
   ▼
リクエスト一覧で状態確認・キャンセル

[Square] ──15分ごとに空き枠を自動取得──→ [アプリ内キャッシュ] ──→ カレンダー表示
（ステップ③で導入。読み取りのみ）
```

## 5. 画面仕様

### 5.1 会員ページ `/m/{token}`（ログイン不要）

- ヘッダーに会員名と種別（月額会員／回数券）を表示
- **空きカレンダー（月表示）**: 日ごとに「空きあり／空きなし／受付対象外（過去・受付範囲外・受付停止日）」を色分け
- 日付を選ぶと、その日の**時間枠一覧**（空きのある枠のみ選択可）を表示
- 時間枠を選び、ひとことメモ（任意・例「打合せで2名利用」）を添えて**リクエスト送信**
- **自分のリクエスト一覧**: 状態（申請中／確定／否認／キャンセル済み）と日時・メモを表示
- 申請中・確定のリクエストは**キャンセル**ボタンあり（実行するとスタッフへ通知メール）
- 無効化されたトークンでアクセスした場合は「リンクが無効です。TORCHまでご連絡ください」を表示

### 5.2 管理画面 `/admin`（パスワードログイン）

- **承認待ち一覧**（トップ）: 会員名・日時・メモを表示し、「確定」「否認（理由ひとこと任意）」ボタン。リクエスト日時順
- **リクエスト検索/一覧**: 状態・期間・会員での絞り込み
- **会員管理**: 登録（名前・メールアドレス・種別）／編集／無効化。登録時に専用リンクを自動発行し、コピー用に表示。**再発行**すると旧リンクは即時無効
- **受付停止日**: 日付単位で会員の受付を止める（理由メモ付き）。Square同期導入前の空き管理のつなぎ兼、導入後も臨時休業・会員受付だけ止めたい日に使用
- **時間枠設定**: 1日の時間枠テンプレート（例: 10:00–13:00 / 13:00–17:00 / 17:00–21:00）を編集可能。ステップ②（手動モード）ではこのテンプレートがそのまま選択肢になる
- **設定**: スタッフ通知先メールアドレス、受付可能期間（何日先まで受け付けるか。初期値60日）、（ステップ③）Square接続設定

### 5.3 承認時の補助表示（ステップ③以降）

- 承認待ちの各リクエストに、Squareキャッシュ上の最新空き状況を併記。リクエスト後にSquare側で枠が埋まった場合は**警告表示**（席数に余裕がある運用のため、ブロックはせず最終判断はスタッフ）

## 6. データモデル（D1）

```sql
members(
  id, name, email, member_type,      -- 'monthly' | 'ticket'
  token UNIQUE,                      -- URLセーフなランダム値（160bit相当）
  is_active, created_at
)
requests(
  id, member_id → members.id,
  date, start_time, end_time,        -- 'YYYY-MM-DD', 'HH:MM'
  status,                            -- 'pending' | 'confirmed' | 'declined' | 'cancelled'
  member_note, admin_note,
  created_at, updated_at
)
closed_dates(date PRIMARY KEY, reason)
availability_cache(date PRIMARY KEY, slots_json, fetched_at)   -- ステップ③
settings(key PRIMARY KEY, value)
ticket_events(id, member_id, delta, reason, request_id, created_at)  -- ステップ④
```

- 二重リクエスト防止: 同一 `member_id`＋`date`＋`start_time` で状態が申請中/確定のものが既にあれば送信をブロック
- 状態遷移: `pending → confirmed | declined | cancelled`、`confirmed → cancelled`。それ以外の遷移は不可

## 7. 空き状況の計算

**ステップ②（手動モード）**:
表示枠 = 時間枠テンプレート − 受付停止日 − 受付可能期間外 − 過去日

**ステップ③（Square同期後）**:
表示枠 = Squareキャッシュの空き枠 − 受付停止日 − 受付可能期間外 − 過去日
（Squareキャッシュが空／未取得の日は「空き情報取得中」として選択不可表示）

- 会員の確定リクエストは席数消費として扱わない（Squareに書き込まない決定と整合。定員管理はしない）

## 8. Square同期設計（ステップ③）

- **取得方法**: Square Bookings API `SearchAvailability` を Workers の cron トリガー（15分間隔）で呼び、今日〜受付可能期間（初期60日）の空き枠を `availability_cache` に保存
- **対象**: 管理画面で設定するロケーションID・サービス（バリエーション）ID。設定手順はステップ③開始時に福田さんと一緒に実施
- **認証**: Squareのアクセストークンを Workers の secret（`SQUARE_ACCESS_TOKEN`）に保存。コード・リポジトリには含めない
- **障害時**: API失敗時は既存キャッシュを使い続け、会員ページに「◯月◯日 ◯時◯分時点の空き状況」と取得時刻を常時表示。取得が24時間以上止まった場合はスタッフへ通知メール
- **レート**: 15分間隔×1リクエスト系で、Squareのレート制限には遠く届かない想定

## 9. 通知設計（Resend）

| きっかけ | 宛先 | 内容 |
|---|---|---|
| リクエスト送信 | スタッフ | 会員名・日時・メモ・管理画面リンク |
| 確定 | 会員 | 確定した日時・注意事項 |
| 否認 | 会員 | 対象日時・スタッフのひとこと理由 |
| 会員キャンセル | スタッフ | 会員名・対象日時 |
| 同期停止（24h以上） | スタッフ | 障害の旨（ステップ③） |

- `RESEND_API_KEY` 未設定時は送信をスキップしログのみ（booking-systemと同じ。開発中の誤送信防止）
- メールが届かなくても管理画面・会員ページの一覧で状態は必ず確認できる（メールは補助、DBが正）

## 10. セキュリティ

- 会員トークン: 推測不可能なランダム値。URLに含まれる性質上、ログに書かない・エラーメッセージに出さない。漏洩疑い時は再発行で即無効化
- 管理画面: パスワード（Workers secret `ADMIN_PASSWORD`）＋セッションCookie。booking-systemの実装を踏襲
- Squareトークン・Resendキー: すべてWorkers secretで管理
- 会員ページ・管理画面とも `robots.txt` と `noindex` で検索エンジン除外

## 11. エラー処理まとめ

- 二重リクエスト → 送信時にブロックし案内表示
- 無効トークン → 案内ページ（連絡先つき）
- Square API障害 → キャッシュ表示＋取得時刻注記＋24h超でスタッフ通知
- メール送信失敗 → 処理自体は成功させ、ログに記録（一覧で確認可能）
- 承認時に枠が埋まっていた → 警告表示のみ（判断はスタッフ）

## 17. 改修パッケージ「ステップ⑤（会員UX改善）」（2026-07-25 福田さん承認）

運用開始後のフィードバックによる改修。診断で確定した前提: 受付期間は本番settingsで180日に変更済み（コード変更不要）。Square同期が動いていなかった原因はロケーションID/サービスID未入力（→ §17.5 で解決）。メール未達の原因は RESEND_API_KEY 未設定（実装対象外・運用設定）。

### 17.1 時間選択の30分単位化（時間枠テンプレート廃止）

- 会員は日付選択後、**開始時刻と終了時刻をそれぞれ30分刻みのプルダウン**で選ぶ（例 10:30〜15:00）
- 選択範囲は新設定「受付時間帯」`open_start`/`open_end`（既定 10:00〜21:00、管理画面で30分刻み選択・open_start < open_end 検証）
- 旧 `slots`（時間枠テンプレート）設定は**廃止**: getSettings から除去、設定画面の該当欄は受付時間帯欄に置換。findSlot/parseSlotsText/slotsToText は不要になる（関連テストも整理）
- POST検証: 開始/終了が30分刻み・受付時間帯内・開始<終了。違反は error=invalid（「終了時刻は開始より後にしてください」等）
- 二重防止は従来どおり 同一会員・同一日・同一開始時刻（部分UNIQUE）。レンジの重なりは禁止しない（席に余裕がある運用・スタッフが承認画面で判断）
- Square同期有効時の空き判定は**日単位**に変更: その日のキャッシュに空き開始時刻が1つも無ければ「この日はSquare側で空きがありません」で受付不可（未取得日は従来どおり「取得中」）。枠単位の照合は廃止
- 承認画面の「Square側で埋まった可能性」バッジは**レンジ重なり近似**に変更: キャッシュの空き開始時刻のうち start<=t<end に入るものが1つも無ければ表示

### 17.2 カレンダーに自分の予約マーク

- 会員カレンダーの日セルに色付きドット: 申請中=橙・確定=緑・否認=赤（同日複数時の優先度 確定>申請中>否認、1点のみ）
- 表示月の範囲で requests を別クエリ取得（status IN pending/confirmed/declined、hidden除外不要=マークは非表示操作と独立でもよいが、実装簡素化のため非表示行はマークも消してよい）
- カレンダー下に凡例を表示

### 17.3 リクエスト受付確認メール（会員宛）

- EmailType に `requested_member` を追加。リクエスト送信成功時、従来のスタッフ宛 `requested` に加えて会員本人へ「リクエストを受け付けました。結果は追ってお知らせします」を送る（Resend未設定時は従来どおり記録のみ）

### 17.4 「あなたのリクエスト」一覧の非表示

- requests に `hidden_by_member INTEGER NOT NULL DEFAULT 0`（migration 0004。§17.1 の open_start/open_end シードも同居）
- 否認・キャンセル済みの行にのみ「非表示」ボタン → POST `/m/:token/requests/:id/hide`（本人＋終了状態のみ・meta.changes判定）
- 会員一覧・カレンダーのマークから消える。管理画面の一覧には残る（記録保全）

### 17.5 Square設定ヘルパー

- 設定画面に「Squareから一覧を取得」→ 認証配下のGET（例 `/admin/settings?square=1`）で Workerが Locations API と Catalog（予約サービス）を取得し、ロケーションとサービスを**プルダウン選択**できるようにする（ID手入力も残す）
- `src/core/square.ts` に fetchLocations / fetchBookableServices を追加（防御的パース・例外は {ok:false} 化・テストは注入fetcher）。実Square APIとの形状差はこの機能の結合確認で吸収する
- 取得失敗時は日本語エラーメッセージ＋従来の手入力継続

### 17.6 既存テストへの影響（重要）

slots廃止により settings/member-requests/member-square/admin-closed-settings 系の既存テストの一部が前提から変わる。計画書で「修正する既存テストの明示リスト」を必ず提示し、それ以外の既存テストは変更しない。

## 18. 追加改修: Square空きゼロ日のカレンダー表示（2026-07-25 福田さん承認）

- 会員カレンダーで、Square同期有効時に「取得済みかつ空き開始時刻ゼロ」の日を受付停止日と同様の**グレー表示＋「×」マーク＋選択不可**にする
- 表示優先: 「停」（受付停止日）＞「×」（Square空きなし）。過去日・期間外セルは従来どおり
- ×セルにも自分の予約ドットは表示する（確定後にSquare側が埋まったケースでも自分の予約が見える）
- カレンダー下（同期有効時のみ）に注記「×の日はSquare側の空きがありません」を表示
- 未取得日は従来どおり通常表示（クリックで「取得中」）。同期無効時は見た目の変化なし。POST検証は既存の unavailable 判定のまま変更しない
- 実装: 表示月全体のキャッシュを既存 getCachedStarts で1回読むだけ（Squareへの新規通信なし）
- テスト: member-square.test.ts に1件追加（累計139件）
